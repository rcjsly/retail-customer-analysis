# 业务分析与验证设计

## 分析委托
角色：零售经营分析师。业务读者：经营负责人及客户运营团队。决策：最近完整月的经营变化应优先排查订单规模、客单变化，还是核心客户与商品集中风险；是否值得启动二购运营实验。

数据仅支持发票交易侧分析。没有访客、广告、库存或成本，不能把订单量变化拆成真实流量×转化率，也不能判断利润、库存周转或供应链履约。

## 分析顺序
1. 建立金额、订单、客户、时间窗口定义，检查ID缺失和非商品项；记录排除与敏感性。
2. 对最近两个完整月按“销售额=订单数×客单价”作恒等分解。固定先订单后客单的分解顺序，交互项归入客单影响；不同顺序分配会不同，总变化必须一致。
3. 用国家、商品、客户金额贡献作定位；排名只能描述集中程度，不能推出增长原因。大额客户可能是批发商，需业务核查。
4. 把客户缺失与经营盘分离，公开客户覆盖率；用完整90天窗口算再次购买，月度Cohort剔除不完整尾月。
5. 规则分群仅按“最近90天是否下单”和“历史订单数是否≥2”分成四类，规则可解释，不声称模型预测准确或能提升收益。

## 可验证假设和动作
|待验证假设|现有证据能做什么|补充数据/验证|
|---|---|---|
|销售变化主要来自购买规模|订单与客单恒等分解|流量、渠道和定价记录，后续识别原因|
|头部客户影响经营稳定性|金额贡献、订单时间、敏感性|批发合同、客户类型、履约资料|
|单次购买客户有二购运营机会|历史90天二购率和人群规模|触达许可、真实触达日志、随机实验|
|负向交易集中在特定订单|原始负向明细及发票核对|取消原因、退款流水和原单关联|

建议不预填“效果提升”，也不把头部贡献高判为一定不健康。没有实验或准实验，所有动作只为候选策略。

## 二购触达实验设计（尚未实施）
- 入组：完成可核实的首次订单，具备合法触达渠道且同意触达的客户；真实系统必须补齐支付和获客历史，不能沿用本数据的首次观察充当真实新客。
- 随机化：按客户随机分为触达组和对照组，可按国家/客户类型分层，防止同一客户多次入组。
- 主指标：入组后90天内有第二笔有效订单的客户比例，按初始分组分析（ITT），等待全部入组者观察期结束。
- 次指标：每入组客户90天净收入；取得成本后计算贡献利润。护栏：退订投诉、补贴成本、负向交易与履约异常。
- 样本量：用当前可比人群基线p0和业务可接受的最小效果差δ预先计算。历史UCI样本不能替代目标企业基线。未提供δ前不编造“需要多少人”。
- 决策：预先约定效果阈值、置信区间、成本与护栏；不因中途显著就提前结束。多版本需要多重检验控制。
- 限制：这份公开数据没有随机分组、触达或干预信息，因此不能完成实际A/B效果验证。

## 简历与面试使用
本项目应标记“独立公开数据项目”，不是品牌实习、商业客户项目或已经落地的增长项目。只有真实运行、核对并理解代码后，才使用results生成的简历材料。

建议按以下顺序讲述：业务问题→数据来源和限制→指标口径→质量核查→方法与实数发现→行动建议→验证和边界。

需要能回答：
1. 为什么没选预测模型？经营口径和观察窗口应先明确，当前任务以描述与决策支持为主。
2. 为什么缺失ID不填？不能可靠恢复客户，填补会虚增或合并客户；保留交易经营金额但不进入客户指标。
3. 为什么不删极值和重复？批发订单可能真实；无唯一行ID无法证明重复导入，做敏感性并查原单。
4. 90天二购率和月留存为何不同？一个是固定时间内出现另一发票，另一个是不同自然月的活跃状态。
5. 为什么不能说“找到了根因”？恒等分解与集中度是描述性定位，真正原因需要业务记录、实验或可信识别设计。
6. 项目如何复用？完整保存原始文件、下载元信息、口径、SQL与断言，修改来源时先检查字段和范围，不能机械套用。
